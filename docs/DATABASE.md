# Database

The database is **optional**. HifzAI works fully without it: recitation, feedback and the summary screen never touch a database. Supabase is only used to keep a tiny, anonymous record of finished sessions, so you can see how the app is being used.

If `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` are not set in `backend/.env`, `POST /session` answers `201 { "sessionId": null, "saved": false }` and the app carries on.

## What is stored

One row per finished session, in one table: `hifz_sessions`. The schema is in [`backend/db/schema.sql`](../backend/db/schema.sql).

| Column | Type | Rule |
|---|---|---|
| `id` | `uuid` | Primary key, generated by the database |
| `created_at` | `timestamptz` | Defaults to now |
| `surah_number` | `integer` | 1 to 114 |
| `start_ayah` | `integer` | At least 1 |
| `end_ayah` | `integer` | At least `start_ayah` |
| `total_words` | `integer` | Greater than 0 |
| `correct_count` | `integer` | Default 0 |
| `wrong_count` | `integer` | Default 0 |
| `skipped_count` | `integer` | Default 0 |
| `word_results` | `jsonb` | One element per word that has a result, see below |

`word_results` looks like this:

```json
[
  { "wordIndex": 0,  "status": "correct" },
  { "wordIndex": 5,  "status": "wrong", "errorType": "missing_shadda",
    "expected": "أَعْطَيْنَاكَ", "spoken": "اعطيناك" },
  { "wordIndex": 11, "status": "skipped" }
]
```

- `status` is `correct`, `wrong` or `skipped`.
- `errorType` appears on wrong words: `missing_shadda`, `wrong_harakat`, `missing_tanwin`, `wrong_word` or `pronunciation_error`.
- `wordIndex` is the word's position in the surah data (see [`GET /surah/{n}`](API.md)).

## What is deliberately not stored

- **No audio.** It is dropped from memory right after transcription.
- **No identity.** There are no accounts, no names, no e-mail addresses, no IP addresses in the table.
- **No device information.**

## Access rules (Row Level Security)

Row Level Security is switched on for the table, with a single policy:

| Who | Insert | Select, update, delete |
|---|---|---|
| `anon` (a browser holding the public key) | allowed (`allow_anonymous_insert`) | **denied**, because no policy grants it |
| The backend (service-role key) | allowed | allowed (the service role bypasses RLS) |

So rows can be added from anywhere but read back only with the secret key, which lives in `backend/.env` and never reaches the browser. In the current code the browser does not talk to Supabase at all: it posts to the Next.js route, which posts to the backend, which inserts with the service-role key.

## Setting it up

1. Create a free project at [supabase.com](https://supabase.com).
2. Open the SQL editor and run the contents of `backend/db/schema.sql`. It is safe to run again.
3. Put the project URL and the **service role** key in `backend/.env` (`SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`). Restart the backend.
4. Finish a session. A row appears under *Table editor* then `hifz_sessions`.

The service-role key is a secret. Never put it in the frontend or in a `NEXT_PUBLIC_` variable.

## Reading the data

Examples to run in the Supabase SQL editor:

```sql
-- Sessions per surah
select surah_number, count(*) as sessions
from hifz_sessions
group by surah_number
order by sessions desc;

-- Average accuracy per surah
select surah_number,
       round(avg(correct_count::numeric / total_words) * 100, 1) as accuracy_percent
from hifz_sessions
group by surah_number
order by surah_number;

-- The words people get wrong most often
select surah_number, (w->>'wordIndex')::int as word_index, count(*) as times_wrong
from hifz_sessions, jsonb_array_elements(word_results) as w
where w->>'status' = 'wrong'
group by surah_number, word_index
order by times_wrong desc
limit 20;
```
